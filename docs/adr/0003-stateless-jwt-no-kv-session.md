# 認証はステートレス JWT を継続し、KV セッションは採用しない

## Status

accepted

## Context

移行計画の初稿では「KV ベースのセッション管理（isolate 横断のため）」を提案していた。しかしこの前提は誤りである。「isolate 間で共有できない」問題はインメモリ Rate Limit には当てはまるが、JWT には当てはまらない。JWT はステートレスで署名検証のみで完結し、isolate をまたいでも問題なく、DB/KV アクセスを一切要さない。

このシステムでは **JWT トークンそのものがログインセッション**であり、サーバー側に別のセッションストアは存在しない。KV セッションを導入すると毎リクエストで KV read が1回増え、コスト・レイテンシは下がるどころか上がる。

## Decision

- **ステートレス JWT（jose）を継続**する。KV フルセッションは採用しない。
- 権限は ADMIN / MANAGER / MEMBER の3段ロールを JWT クレームで保持。
- **JWT 有効期限を 48h → 12h（≒1営業日相当）に短縮**する。即時失効（秒単位）は要件ではないため、翌営業日には無効化が必ず効く状態で実用十分とする。
- 即時失効が必要になった場合に限り、後日 KV ブラックリスト（失効操作時のみ書き込み、通常時 read 不要）を検討する。フルセッションストアには戻さない。

## Consequences

- 認証検証は外部アクセス0でメモリ内完結。CF Workers 上で最安・最速。
- ユーザー無効化（isActive=false や権限変更）は最大12時間反映が遅れる。スクール運営の性質上許容する。

## 2026-11-13 追記：スライディング更新と絶対期限（#276）

- ステートレス JWT と PC / LINE 共通の LINE OAuth を継続する。LIFF SDK は導入しない。
- JWT / Cookie の有効期限を2時間、更新間隔を15分、初回ログインからの絶対期限を7日とする。それぞれ `JWT_EXPIRES_IN`、`JWT_REFRESH_INTERVAL`、`JWT_ABSOLUTE_EXPIRES_IN` で設定する。
- `requireAuth` は認証済みリクエストの `iat` が更新間隔に達していたら DB から最新のユーザー情報を読み直し、JWT / Cookie を再発行する。通常の検証と未認証リクエストでは DB にアクセスしない。
- 再発行時のロール変更をそのリクエストから反映する。無効化済みなら403、削除済みなら401とし、再発行しない。
- 初回ログイン時刻 `authTime` を再発行時にも引き継ぎ、絶対期限はリクエストごとに検証する。`authTime` のない旧JWTは401とし、一度再ログインを求める。
- 「操作」は認証付きAPIへのアクセスを指す。有効期限は最後の再発行から2時間なので、最後のアクセスからの無操作時間は約1時間45分〜2時間となる。
- 未ログインで User-Agent に `Line/` を含む場合は、戻り先と招待トークンを保持して LINE OAuth へ自動遷移する。`error` があれば自動遷移せず、手動の再試行を表示する。
