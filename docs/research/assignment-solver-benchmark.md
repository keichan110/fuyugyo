# 割当ソルバーのベンチマークとアルゴリズム選定

## 目的

[#184](https://github.com/keichan110/fuyugyo/issues/184) の解決材料。[#177](https://github.com/keichan110/fuyugyo/issues/177) で「自動割当の計算はブラウザの Web Worker で回す（Cloudflare は Free のまま）」ことは決めたが、**どのアルゴリズム／ライブラリで解くか**は一次情報にベンチマークがなく決められなかった。[#178](https://github.com/keichan110/fuyugyo/issues/178) で割当モデル（ハード制約・コスト関数・探索方針）が確定したので、そのモデルを実データ規模で組み立てて実測する。

## 実施日・環境

- 2026-07-14 / macOS (Darwin 25.5.0), Node.js v26.4.0（V8。ブラウザの JS 実行エンジンと同じ）
- 比較対象: 自前の貪欲＋局所探索 / YALPS 0.6.4 / javascript-lp-solver 1.0.3 / highs-js (`highs`) 1.14.2
- ベンチコードは使い捨てプロトタイプ（リポジトリには含めない）。中核ロジックは本ドキュメント末尾に採録する。

## 結論

**自前の「貪欲法 ＋ ランダム再スタート付き局所探索」を採用する。LP/MIP ソルバーは採用しない。**

理由は 3 つ:

1. **#178 のコスト関数は線形計画に載らない。** 公平性 `Σ(actual − target)²` は二次であり、資格構成スコア（枠内の最高 rank と ユニーク rank 数）は `max` と「相異なる値の個数」なので、追加のバイナリ変数なしには線形制約で書けない。LP/MIP に載せるには**公平性を L1（絶対偏差）に緩め、level 項を捨てる**必要がある。つまり MIP は「#178 とは別の目的関数」を厳密に解くことになる。
2. **その線形化モデルを厳密に解いても、#178 の真のコストでは自前探索に勝てない。** highs-js は線形化モデルの最適解を 160〜260ms で返すが、真コストで評価すると自前探索と同等かわずかに劣る（下表）。厳密解が勝てないのは、解いている目的関数が違うから。
3. **求解時間で困っていない。** 自前探索は本命規模で **約 200ms**、最悪ケース（150名 × 4種別）でも 10 再スタートで 160ms。許容待ち時間 10 秒に対して 20〜50 倍の余裕がある。依存ゼロ・Wasm なし・anytime 打ち切り可能・キャンセル可能という運用上の利点がそのまま乗る。

## 実測

### 前提規模

- インストラクター 70名（`scripts/seed-dev-data.ts` 準拠、ACTIVE 90%、資格分布も同スクリプトの重み）。うちスキー部門の候補プールは 52名。
- 対象 = 1か月31日 × シフト種別1（一般レッスン）、希望人数 平日3名 / 土日5名 → 31枠・総希望113名。
- 不可申告: 1人1日あたり UNAVAILABLE 35%・AVOID 12%（人による偏りあり）。対象外セルの既存割当（同日掛け持ち禁止に効く）を 5% の日に付与。
- バイナリ変数（＝候補 × 枠）は本命で 817、最大ケースで 7,294。

★ = 10秒の時間制限で打ち切り（＝制限時間内に解けていない）。

- **YALPS は使えない**。10秒でタイムアウトし、実質何も割り当てられていない解を返す。README が「整数変数は数百個まで」を推奨範囲としていた通り、数百〜数千のバイナリ変数は完全に射程外だった。
- **jsLPSolver も使えない**。10秒使い切ったうえ、不足を1〜3名残す（＝最優先制約を満たせていない）。
- **highs-js は速い**（数百 ms で線形化モデルの最適解）。ただし ①Wasm バイナリ 3.17MB をバンドルに抱える ②目的関数を L1 公平性へ緩め level 項を捨てる必要がある ③その代償を払っても真コストでは自前探索に勝てない。**採用しない**が、将来モデルが本当に線形で書けるようになった場合の第一候補として記録しておく。
- glpk.js は GPL-3.0 のため今回は評価対象外（#177 の判断を維持）。

### 自前探索の時間予算（再スタート数と質の関係）

| 規模               | 再スタート10 | 50            | 200            | 1000            |
| ------------------ | ------------ | ------------- | -------------- | --------------- |
| 本命 70名/1種別    | 48ms / 141.9 | 202ms / 141.9 | 771ms / 141.9  | 3,905ms / 141.9 |
| 上振れ 150名/1種別 | 46ms / 519.1 | 233ms / 519.1 | 931ms / 519.1  | 4,359ms / 519.1 |
| 上振れ 150名/4種別 | 157ms / 99.3 | 778ms / 99.2  | 3,090ms / 99.1 | 10,000ms / 99.0 |

（各セル = 実測時間 / 真コスト。3シードの平均）

**質は再スタート10回で頭打ち**になる。それ以上回しても真コストはほぼ動かない（最大ケースで 0.3% 未満）。局所探索が弱くて同じ局所解に落ちているのではないことは、線形化モデルの厳密解（highs-js）と同水準のコストに達している事実が裏づける。

したがって:

- **時間予算は 1 秒**（実測はどの規模でも 200〜450ms に収まる）。「10秒まで許容」の余裕は**質の向上には使えない**ので使わない。
- 打ち切り条件は **「再スタート20回 または 経過1秒のいずれか早い方」**。予算超過時は best-so-far を返す anytime 動作（実装済み・検証済み）。
- 上振れ規模（150名 × 4種別 = バイナリ相当 7,294）でも 160ms なので、**モバイル端末で 5〜10 倍遅くても 2 秒以内**に収まる。ブラウザでの追加実測は行わない（純 JS・Wasm なしで V8 上の相対性能はそのまま効くため）。実装時に実端末で一度確認すれば足りる。

### 重みの妥当性（#178 §4 の初期値）

`W_SHORT=10000 / W_AVOID=100 / W_FAIR=1 / W_LEVEL=0.1` を**そのまま採用する**。ベンチで意図通りの挙動が確認できた:

- 候補に余裕がある規模（1〜2種別）では **不足0・AVOID 0** を達成し、公平性と資格構成の調整に探索を使う。
- 候補が逼迫する規模（4種別 = 総希望452名を候補52名で埋める）では **AVOID を17件踏んででも不足を0にする**。これは「埋められないときは AVOID の人を入れてでも枠を埋める」という #178 の優先順位そのもの。
- 逼迫時に公平性の値がむしろ小さくなる（27.8）のは、全員が上限近くまで割り当てられて偏りようがなくなるため。異常ではない。

## Web Worker 統合方式

- **Vite ネイティブの worker import** を使う: `new Worker(new URL('./auto-assign.worker.ts', import.meta.url), { type: 'module' })`。Vite が worker バンドルを自動生成するため追加設定は不要（Wasm を持ち込まないので、Workers ランタイムや `locateFile` の問題も発生しない）。
- **キャンセル**: モーダルを閉じる / 「別の案を出す」を連打された場合は `worker.terminate()` して作り直す。探索は純粋関数なので中断に副作用がない。
- **進捗通知**: 再スタート1回ごとに `postMessage({ type: 'progress', restarts, bestCost })`。ただし実測200〜450msなので、UI は**進捗バーではなくスピナーで足りる**（進捗表示は実装しない）。
- 入力（`AutoAssignInput`）は構造化クローンで渡せる素の JSON。Worker 側は DB もネットワークも触らない。

## 採録: 中核ロジック（プロトタイプ）

実装時はこれを TypeScript へ移植する。`prep`（前処理済み構造）の組み立ては #178 §9 の `AutoAssignInput` から機械的に導ける。

```js
// コスト増分（貪欲・局所探索の両方で使う）
function deltaAdd(prep, state, si, i) {
  const slot = prep.slots[si];
  const members = state.assign[si];
  const shortDelta = members.length < slot.need ? -W_SHORT : 0;
  const avoidDelta = prep.avoidFlag[si].has(i) ? W_AVOID : 0;
  // 二乗偏差の増分: (w+1-t)² − (w-t)² = 2(w−t)+1
  const fairDelta = W_FAIR * (2 * (state.work[i] - prep.target[i]) + 1);
  const levelDelta = W_LEVEL * (levelScore(slot, members) - levelScore(slot, [...members, i]));
  return shortDelta + avoidDelta + fairDelta + levelDelta;
}

// 初期解: 候補が少ない枠から、コスト増分が最小の人を1人ずつ（同点はシード付き乱択）
function greedy(prep, rand) {
  const state = emptyState(prep);
  const order = [...prep.slots.keys()].sort(
    (a, b) => prep.slots[a].candidates.length - prep.slots[b].candidates.length,
  );
  for (const si of order) {
    const slot = prep.slots[si];
    while (state.assign[si].length < slot.need) {
      const best = argMinWithRandomTieBreak(
        slot.candidates.filter((i) => !state.dayUsed[slot.date].has(i)),
        (i) => deltaAdd(prep, state, si, i),
        rand,
      );
      if (best === undefined) break; // 候補が尽きた ＝ 不足
      addMember(prep, state, si, best);
    }
  }
  return state;
}

// 局所探索: (a) 枠内の1人を別候補と交換 (b) 2枠間で人を交換 (c) 空席埋め
// 改善する変更のみ適用し、改善が 4000 手続かなければ収束とみなす
// 上位ループでシードを進めながら再スタートし、best を採る（20回 or 1秒で打ち切り）
```

- `levelScore` は #178 §6 の式（`2 × ceiling + spread`、段数非依存）。枠内メンバーの rank 配列だけから計算でき、`Set` 1つで済む。
- 公平性の増分が定数時間で書けるのが効いていて、1回の再スタート（貪欲＋数千手の局所探索）が数 ms で終わる。

## 未確認・残る前提

- ベンチの可用性データは合成（UNAVAILABLE 35% / AVOID 12%）。**実データの申告密度は運用開始まで分からない**。申告が極端に多い（例: 全員が7割の日に UNAVAILABLE）と候補が枯れて不足が増えるが、これはアルゴリズムの限界ではなく人員の限界であり、#178 の「不足＋理由内訳」で説明する設計で足りる。
- 祝日・年末年始の判定は本ベンチでは土日のみで近似した（実装では `japanese-holidays` を使う。#178 §9）。枠数がわずかに変わるだけで、求解時間の結論には影響しない。
- 実端末（特にスマートフォン）での実測は未実施。純 JS のため V8 の相対性能がそのまま効く前提で、20倍の余裕を根拠に省略した。
