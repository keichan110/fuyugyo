# メンバー向け表示専用 read を Cloudflare Workers Cache API で短 TTL キャッシュする（無効化は TTL 一本）

## Status

rejected（見送り）— 設計記録として温存する

**現時点では実装を見送る。** 現規模（同時 10〜20 人・書き込みは管理者中心で低頻度）では、本設計の実装コスト（`withCache`・ユーザー単位レート制限・クライアント担保機構・8 群のテスト、数日規模）と恒久的な保守・認知負荷に対し、得られる便益が見合わないと判断した:

- **体感速度**: 削減できるのは D1 読み取り＋組み立ての数十 ms のみで人間の知覚閾以下。加えてクライアントは既に TanStack Query がキャッシュしており、エッジキャッシュの効きしろは小さい。
- **コスト**: Cache API は Worker 呼び出しを減らさない（Workers 課金の削減はゼロ）。D1 読み取り課金の節約も現トラフィックでは月十数セント規模で無視できる。
- 設計が多数の安全機構（安全不変条件 1〜7）を必要とすること自体が、複雑性が便益に対して過大であるシグナル。

代わりに、より低コストな **TanStack Query の `staleTime` 見直し**で体感改善を図る（GitHub issue #210）。

**本 ADR は破棄せず設計記録として残す。** 下記の**再評価トリガ**が観測されたら本 ADR を出発点に再検討する:

- 同時ユーザーが大幅増（数百〜千人規模）
- D1 読み取り課金が体感できる額になる
- 繁忙期に**実測された**特定画面のレイテンシ問題が出る

再評価して実装する場合の受理条件（当時の想定）: `withCache` 相当をエッジ側で `/agenda`・`/attendance` に適用し、鮮度 SLA の担保機構（mutation 時 invalidate ＋ `refetchInterval≈TTL`）をクライアント側に実装、末尾「必須テスト」①〜⑧が green になった同一変更をもって `accepted` とする（認証済み read 用の新 Rate Limit binding 追加と、それに伴う ADR 0004 の適用範囲更新を含む）。

## Context

システムは 2026 年末に新規稼働予定で、リアーキ後まだ繁忙期を通していない。パフォーマンス上の実測された痛みは無い（予防的最適化）。一方、繁忙期には多数の MEMBER（インストラクター、肌感 10〜20 人・将来増加余地あり）が週末に向けてシフト表・自分の割り当てを**同時に閲覧**する。これらのシフト閲覧ビューと各種マスタは全員で共有された同一データであり、書き込みは MANAGER/ADMIN 中心・低頻度という前提がある。

論点は「読み取りレイテンシを将来のスケールに向けて下げる保険を、どの層で・どの道具で持つか」だった。GET ルートは全 65 本で、いずれも `requireAuth`（Cookie の JWT 必須）を通す。JWT 検証はステートレスで D1 ルックアップを行わない（ADR 0003）ため安価。すなわち削減余地があるのは Worker 呼び出しではなく **D1 の行読み取りとオリジン計算**である（Cache API はキャッシュ判定が Worker の内側で走るため、Worker 呼び出し自体は減らない）。

## Decision

**メンバー向けの純粋な表示専用 read に限り、`caches.default`（Cache API）で短 TTL（60s）のキャッシュを行う。適用は認可通過後・ハンドラ内での明示 opt-in とし、キャッシュキーは Cookie 非依存にする。無効化は行わず、古さは TTL でのみ bound する。**

当初は「シフト閲覧系＋各種マスタ」を広くキャッシュ対象にしようとしたが、アドバーサリアルレビューで**それらの多くが実は書き込み判断の入力**であることが判明したため、対象を大幅に絞り込んだ。詳細は下記「安全不変条件 5」と「キャッシュしないもの」を参照。

### 安全不変条件

1. **認可通過後にのみキャッシュを読み書きする（エッジ側）。** Cache API（`caches.default`）の読み書きは `requireAuth`（＋ `requireRole`）を通過した後、ハンドラ内で行う。Worker はリクエストごとに必ず走り認証を検証するため、**エッジキャッシュ経由の認証バイパスは原理的に起こらない**。
2. **クライアント（ブラウザ HTTP キャッシュ）には絶対にキャッシュさせない。** 不変条件 1 の「毎回 Worker が走る」保証は**エッジ側だけ**に成立し、ブラウザの HTTP キャッシュには成立しない。もし認証必須レスポンスをブラウザがキャッシュすると、ログアウト・同一プロファイルでのユーザー切替後も Worker に到達しないまま最大 TTL 秒 前セッションのデータ（全員の氏名・勤務）を再表示しうる。これを塞ぐため、**TTL 用の `Cache-Control: max-age` は Cache API に `put()` する複製にのみ付け、クライアントに返す MISS/HIT レスポンスは必ず `Cache-Control: no-store, private` に置き換える**（キャッシュ制御を「エッジ保存用」と「クライアント返却用」で分離する）。これは任意ではなく**必須実装要件**とする。
3. **キャッシュキーは Cookie を含めず、かつ「検証済み・正規化済みの意味的パラメータ」だけから組み立てる（生の query 文字列をそのまま使わない）。** Cookie を含めないのは、同一認可ティアの全ユーザーが 1 エントリを共有しヒット率を確保するため（全対象 GET は認可上 `requireAuth` のみで、レスポンスがユーザー識別で分岐しない）。生の query をそのままキーにすると、認証済み MEMBER が `?dates=…&x=<毎回異なる値>` や意味的に等価な非正規化パラメータ（順序違い・重複・`limit` の別表現）を送るだけで**キャッシュを無限に分割**でき、各要求が別キー MISS → D1 読み取り＋`cache.put` を誘発してホットエントリを追い出せる（D1 負荷低減という目的を低権限ユーザーが逆に増幅する、キャッシュ汚染／DoS 増幅）。これを塞ぐため: **(a) 未知の query パラメータは Zod `.strict()` 等で 400 拒否する、(b) 既知パラメータは正規化してからキーに使う**（`dates` は形式検証・重複除去・昇順ソート、`limit` は許容レンジへ丸め、`departmentCode` は固定語彙照合、`cursor` は形式検証）。キーは URL 生文字列ではなく、この**正規化後の値から決定的に生成**する。ただし正規化・未知パラメータ拒否は**表記ゆれしか防がない**——`cursor`/`dates` に**相異なる有効値**を連続送信すれば依然として別キー MISS を量産できる。これには不変条件 6 の 2 段（入力空間の窓限定＋レート制限）で対処する。
4. **適用は明示 opt-in ヘルパー**（`withCache` 相当）で対象ルートに手で付与する。GET 全体へのミドルウェア自動適用（＋除外リスト）は、新規 `/me` 系ルート追加時に除外し忘れるとユーザー固有データが共有キャッシュへ漏れる fail-open のため採らない。
5. **古さが不変条件を緩めてはならない（キャッシュ可否の判定基準）。** ある GET をキャッシュしてよいのは、それが **(a) 純粋な表示専用**であり、かつ **(b) クライアントの read-modify-write のベースや、認可・業務制約の判断入力になっていない**場合に限る。言い換えると「そのレスポンスが最大 TTL 秒 古くても、サーバが独立に強制している不変条件を一切緩めない」ことが必須。サーバが該当制約を書き込み時に強制していないなら、その read はキャッシュしない（キャッシュの有無に関わらず存在する穴を、キャッシュが時間方向に広げてしまうため）。
6. **キャッシュ汚染と D1 増幅を 2 段で bound する。** 有効値の連打によるキー量産（不変条件 3 では防ぎきれない残余）に対し、次の 2 つの性質を分けて対処する。
   - **キャッシュ固有の害＝ホットエントリの追い出し（汚染）**: 「業務上必要な期間の窓」だけでは不十分である——`attendance` は 1〜7 個の任意日付を受けるため、窓内でも**日付集合の組合せで有効キーが爆発**し、レート制限は速度を落とすだけで長時間の汚染を防げない。したがって `withCache` を適用するのは、**UI が実際に発行する canonical（正準）なクエリ形状だけ**に厳しく限定する:
     - `attendance`: UI が使う固定パターンのみキャッシュ（現状 `CurrentAttendance` の today/tomorrow など、列挙可能な少数の today 起点パターン）。それ以外の `dates` 集合は**常にキャッシュをバイパス**（`cache.match`/`cache.put` を行わず D1 直読み）。
     - `agenda`: `cursor` を**ページ送りグリッドに整列**した値かつ**有限窓（例: シーズン ± 数か月）内**のみキャッシュ。グリッド非整列・窓外はバイパス。これで cursor 空間は組合せでなく線形かつ有限（窓 ÷ ページ幅）に収まる。
     - 結果として、cache に書き込まれるキー総数は**有限小集合**に上限づけられ、攻撃者が有効値を変えても素通し扱いになるだけでホットエントリを追い出せない。**その上限を先送りせず、現行 UI の実呼び出しに基づき下表で確定する**（バイパスは 400 拒否ではなく素通しとし、正当な非定型参照を壊さない）。

     **canonical クエリ形状と最大キャッシュキー数**（実装は現行クライアントの呼び出しに基づく）:

     | エンドポイント | キャッシュする canonical 形状                                                                                                                                         | バイパス（`cache.match`/`put` しない）する形状                                                             | 最大キー数                              |
     | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------- |
     | `attendance`   | `dates` が today 起点の固定パターン（`[today]` / `[today, tomorrow]`＝`CurrentAttendance` が発行）・`departmentCode` 無                                               | それ以外の任意 `dates` 集合（とくに `UpcomingShifts` の**ユーザー可変な日付集合**）、`departmentCode` 指定 | ≒ 2（today 進行に伴い日次でローテート） |
     | `agenda`       | `cursor` がキャッシュ窓（シーズン ±1 か月、≒183 日）内・`direction ∈ {future, past}`・`limit = 14`（クライアント固定値のみ）・`departmentCode ∈ {ski, snowboard, 無}` | 窓外 `cursor`（深いリンク起点日を含む）、`limit ≠ 14`                                                      | ≒ 183 × 2 × 3 = **1098**                |

     合計の最大キャッシュキー数はおおむね **~1100 件**（各レスポンスは小さな JSON）で、Cache API の容量に対して十分小さく、攻撃者が有効値を変えても上記以外は素通しのため cache に載らず、ホットエントリを追い出せない。`UpcomingShifts` の可変日付集合を**バイパス**にするのは、それがユーザーごとに異なりキャッシュ効果が薄い一方でキー空間を組合せ的に膨らませるため。窓・`limit` 固定値・部門数が変われば上限も比例して再計算する。

   - **一般的な害＝認証済み連打による D1 読み取り増（ベストエフォート防御＋残余リスク受容）**: これは**キャッシュの有無に関係なく全 read 共通**の性質で、対策の主役はキャッシュ設計ではなく**レート制限**である。ただし 2 点を正直に区別する:
     - **既存の ADR 0004 の機構はそのまま流用しない**——ADR 0004 は認証系専用で `rateLimit()` は `CF-Connecting-IP` をキーに `AUTH_RATE_LIMITER` を使う。これを認証済み read にそのまま流用すると (i) 同一 NAT の正規スタッフが相互に 429、(ii) 複数 IP の攻撃者にユーザー上限が効かない。よって**認証済み read 専用の新 Rate Limit binding・バケット・閾値を定義し、キーは JWT の安定ユーザー ID（`user.userId`）とする**新ミドルウェアを設ける（認証後・D1 読み取り前に評価）。これは ADR 0004（認証系のみ・IP キー）の適用範囲を意図的に拡張するもので、本 ADR 0013 を最新の決定として ADR 0004 をこの点で上書き（オーバーライド）する。
     - **ただしこれは「厳密なグローバル上限」ではなく、POP 単位・結果整合のベストエフォート防御である。** Workers Rate Limiting binding のカウンタは Cloudflare ロケーション単位かつ同一ロケーション内でも eventually consistent なため、認証済み攻撃者が複数地域のプロキシを使えば同じ `user.userId` でも POP ごとに上限を消費でき、並行バーストでは単一 POP でも超過分が D1 に到達しうる。**したがって「複数 IP 合算で必ず 429」「それ以上 D1 に一切到達しない」といった厳密保証はしない。** これを残余リスクとして受容する根拠: (a) 攻撃者は**認証済み MEMBER（信頼済みスタッフ）**に限られ匿名攻撃面ではない、(b) 被害は D1 の**読み取りコスト増に限定**され、データ破壊・漏洩・制約違反は起きない（不変条件 1・5 で担保）、(c) 本 ADR は予防的最適化であり、この規模で厳密強制のために `user.userId` シャードの Durable Object を D1 前段に置くのは過剰。将来この増幅が実害化したら、その Durable Object 方式（グローバル強整合カウンタ）へ escalate する余地を残す。
     - **具体パラメータ（初期値・チューナブル）と正規利用の非阻害**: 対象ルートは本 ADR のキャッシュ対象読み取り（`agenda`/`attendance`）とし、閾値は**正規利用の最大量から逆算**して余裕を持たせる。1 ユーザーの通常最大量は、ダッシュボード初回表示（`attendance` today/tomorrow＋直近 `agenda`）＋ agenda ページング数回＋ `refetchInterval` 60s ポーリング（対象 2 種で ≒2 req/min）で、ピークでも概ね数〜十数 req/min に収まる。よって初期値を**ユーザー単位 60 req / 60s・バースト 20**（新 binding、キー `read:${user.userId}`）とする——正規利用（画面遷移・ページ送り・定期再取得を含む）はこの上限に達しない。**429 時のクライアント方針**: 定期再取得が 429 になっても致命ではなく、次の interval で指数バックオフ再試行し、成功するまで直近の表示を保持する（SLA は「更新が届くまで」の緩い上限なので、一時的な 429 は SLA 内で回復する）。閾値・period・burst は運用計測で調整するチューナブル値であり、初期値の妥当性（正規利用が 429 にならないこと）は必須テストで固定する。
7. **キャッシュはベストエフォートであり、キャッシュ基盤の障害でメンバー表示を落とさない（fail-open）。** `withCache` は Cache API を必須経路にしない。**`cache.match` が例外/タイムアウトを返したら、ログ・メトリクスを残して必ず D1 直読みへフォールバック**する（MISS 同等に扱う）。**`cache.put` の失敗はレスポンスに一切影響させず**、観測（ログ/メトリクス）のみ行う（`waitUntil` 内で握りつぶす）。すなわち Cache API の一時障害でも `agenda`/`attendance` は 5xx にならず、性能が一時的に落ちるだけに留める。この 2 経路（match 例外→D1 退避、put 失敗→無影響）は、例外を投げる Cache テストダブルで必須テストに含める。

### キャッシュ対象と TTL（無効化は TTL 一本）

安全不変条件 5 を満たすのは、**メンバーが大量に同時閲覧する表示専用サーフェスだけ**である。これは奇しくも本 ADR の元動機（繁忙期のメンバー同時閲覧）そのもので、読み取りホットスポットと安全に倒せる集合が一致する。

| 対象                                                                   | 用途                                 | TTL         | 無効化       |
| ---------------------------------------------------------------------- | ------------------------------------ | ----------- | ------------ |
| `shifts/agenda`（`ShiftAgendaViewer`＝メンバーのシフト閲覧）           | 表示専用（書き込み判断に使われない） | 短め（60s） | **TTL のみ** |
| `shifts/attendance`（ダッシュボードの出勤状況 `CurrentAttendance` 等） | 表示専用（書き込み判断に使われない） | 短め（60s） | **TTL のみ** |

**エッジ無効化は行わず TTL のみで古さを bound する。** 書き込み時の `cache.delete()` は使わない。理由: Cache API には**キーの前方一致・ワイルドカード削除が無い**（`cache.delete()` は完全一致 1 件ずつ）が、`agenda`/`attendance` は `cursor`／`departmentCode`／日付配列などで**キー変種を複数持つ**ため、書き込み時に該当変種を列挙して確実に消す保証が持てない。列挙漏れが古さより悪い（一部だけ消えて不整合が長引く）ので、短 TTL（60s）一本に倒す。厳密な無効化（世代付きキー＋書き込み時の世代更新）は全 POP 共有の状態ストア＝ KV/D1 を要し Cache API を選んだ意味が薄れるため採らない。**ただし「表示専用だから古さは無害」とは扱わない**——シフト表は業務指示（work order）であり、後述の鮮度要件を満たすためエッジ TTL だけでなくクライアント側の担保機構を併用する。

### 鮮度要件（プロダクト SLA）と担保機構

**鮮度要件**: MEMBER が見るシフト表示（`agenda`/`attendance`）は、管理者の割当変更・取消が**通常運用で数十秒〜遅くとも数分以内**に反映されること（ハードなリアルタイムは要求しない。プロダクト判断として確定）。

この要件はエッジ TTL 単体では満たせない（TanStack Query は stale になっただけでは表示中クエリを再取得しないため、開いたままの画面が任意に長く古くなりうる。かつエッジ側は後着 put で上限非保証）。よって**本変更のスコープにクライアント側の担保を含める**:

1. **割当 mutation 時に `agenda`/`attendance` のクエリキーも invalidate する**（現状 `useUpsertAssignments` は `calendar`/`assignment-editor`/`list` のみ）。これは**再クエリを促す**役割であって「即時反映」ではない——エッジは TTL のみ・delete しないため、invalidate 後の再取得がウォーム済みエントリに HIT すると書き込み前の本文を受け取りうる。実反映は最大エッジ TTL 遅れ、すなわち SLA 内に収まる（この invalidate が無いと、クライアントは自前の TanStack Query キャッシュを握ったまま再取得トリガまで更新されず、SLA を超える）。
2. **`agenda`/`attendance` に `refetchInterval ≈ エッジ TTL（60s）` を付与する**。別クライアントの変更も、開いたままの画面が定期再取得で拾う。1・2 いずれも「クライアントに再取得させる」機構であり、実際の鮮度は最終的に**エッジ TTL に律速される**（即時ではなく SLA 内）。
3. **担保機構は「cached サーフェスを描画する全経路」を覆うこと（部分適用は不可）。** とくに `ShiftAgendaViewer` の「以前を表示」で読み込む**過去ページは現状 `useShiftAgendaFuture`（Infinite Query）の外で、`fetchShiftAgendaPage` を直接呼び `pastPages` の React state に保持**しているため、上記 1・2 は過去ページに届かない。`PUT /shifts/assignments` は過去月を拒否しないので、過去シフトの訂正・取消後も過去ページ表示中の MEMBER が無期限に古い業務指示を見続けうる。よって過去ページも **TanStack Query（Infinite Query）管理へ統合して interval・invalidation の対象に含める**か、少なくとも**割当 mutation 時に `pastPages` を破棄／再取得し、定期再取得でも更新する**ことを本変更の必須要件とする。

この担保により、画面上の実効的な古さは**通常運用で概ね「エッジ TTL＋再取得間隔」＝おおむね ≤ 2 分**に収まり、鮮度要件を（未来ページ・過去ページ・attendance の全表示範囲で）満たす。読み取り一貫性の観点では、エッジの後着 put レース（前述）が稀に数秒の追加遅延を生じうるが、これは数十秒〜数分という許容幅に十分収まる。これは**統計的・通常運用上の上限**であって暗号学的な厳密保証ではない点は明記する（厳密上限が要るなら世代キー/purge が必要だが、本要件はそれを求めない）。

### キャッシュ**しない**もの（安全不変条件 5 で除外）

- **read-modify-write のベース／編集の競合判断入力**: `shifts/calendar`、`shifts/`(list)。`useShiftManagerController` が `useShiftCalendar` の結果から競合ラベル（`conflictLabelById`）と保存ベースを組み立て、`useUpsertAssignments` は保存後に `calendar`/`list` を invalidate する。`PUT /shifts/assignments` は**セル単位の全置換**で、同日二重割当を**サーバ側で拒否していない**ため、古い calendar を土台にすると二重割当・ロストアップデートが永続化しうる。**表示専用ではない**ので除外。
- **マスタ系（departments / shift-types / department-shift-types / certifications / certification-requirements）**: いずれも編集・認可・検証の入力になっている（`InstructorDrawer` の資格割当、`ShiftTypeSettings`、資格要件エディタ等）。とくに `certifications` の古い一覧は無効化済み資格の再割当に使われうるが、サーバ側は割当時に `is_active` を検証していない（後述の既存ギャップ）。**サーバが該当不変条件を強制するまでキャッシュしない**。
- **編集・context 系 GET**: `shifts/creation-context`、`assignment-editor`、`auto-assign-context`（編集フローの入力データ。低トラフィックでもある）。
- **ユーザー固有 GET**: `auth/me`、`availabilities/me`、`shifts/me/season-stats`（共有キャッシュ不可）。
- **ロール gate 付き管理者専用 GET**: `users`、`invitations`、`availabilities`(一覧) 等（低トラフィックで効果が小さく、キャッシュ面を無駄に広げないため）。

### 可観測性

キャッシュ対象レスポンスに `X-Cache: HIT|MISS` ヘッダを付与し、devtools / `curl -I` および本番で HIT 状況を検証可能にする。

## Considered Options

- **KV をキャッシュ層に使う**: 書き込み時に put/delete でグローバル無効化できる利点があるが、伝播に最大 60 秒かかり「即時」ではない以上、TTL 60 秒の Cache API と実効差が小さい。新規 binding と読み書き課金が増え、余計な状態ストアを持たない ADR 0003 の思想にも逆行するため却下。
- **D1 read replication（Sessions API）**: 古さ管理・無効化バグが原理的に発生せず、レイテンシ最短化には最有力。ただし D1 読み取り課金は減らず、read-your-writes を扱う Sessions API 対応の実装コストが乗る。今回の主目的（レイテンシの保険）に対してオーバースペックと判断し、繁忙期に古さが問題化したら再検討する余地を残して却下。
- **書き込み時の Cloudflare Purge API でグローバル無効化**: 全 POP を即時に消せるが、外部 API 依存・レート制限・キャッシュキー＝実 URL 制約が乗る。現規模では即時性の価値が複雑度に見合わず、将来ユーザーが複数 POP に広がって古さが問題化した時点で引き上げる段階戦略を採る。

## Consequences

- **キャッシュは発生した POP 内のみで、グローバル複製されない**（Cache API の仕様）。無効化は行わず、古さは TTL でのみ bound する。日本のスキースクール 1 校でトラフィックは日本の 1〜2 POP（東京中心）に集中するため、キャッシュのヒット率は十分見込める。
- **許容した古さと read-through レース（鮮度上限は機構的に保証しない）**: 無効化を行わない read-through キャッシュには本質的なレースがあり、**Cache API では鮮度に厳密な上限を保証できない**。Cache API は条件付き put も世代比較も持たないため、次の順序が起こりうる——(1) ある GET が書き込み前の D1 を読み、その `cache.put` を `waitUntil` で遅延させる → (2) 書き込みがコミット → (3) 書き込み後の GET が新しい値をキャッシュ投入 → (4) その**後に**(1) の古い `cache.put` が後着し、新しい値を**上書き**して、その時点から改めて TTL(60s) が始まる。後着の古い投入を機構的に防ぐ手段は無い。したがって「書き込み後 最大 60 秒」や「TTL 失効後に必ず最新へ収束」という**厳密な保証は成立しない**。実務上の古さは概ね「in-flight GET の `waitUntil` 寿命（数秒オーダー）＋ TTL(60s)」に収まり、以降の read が再 populate して自己是正するが、これは保証ではなく傾向である。**この機構的な非保証が業務上許容されるのは、鮮度要件（数十秒〜数分）に対して十分小さいからである。** シフト表は業務指示であり「表示専用だから何秒古くてもよい」わけではないが、後着 put レースが生む追加遅延は数秒オーダーで、確定した鮮度 SLA（上記「鮮度要件」）の許容幅に収まる。そのうえで実効的な画面鮮度は、エッジ TTL 単体ではなく上記「担保機構」（mutation 時 invalidate＋`refetchInterval≈TTL`）で bound する。**もし将来この SLA が「数秒の厳密上限」に厳格化されたら、TTL のみでは不可であり**、「書き込みと原子的に更新する世代値をキャッシュキーへ組み込む」または「確実な purge」の導入が必要になる（いずれも全 POP 共有の状態ストア＝ KV/D1 を要し、Cache API を選んだ意味が薄れる）。現行 SLA はそれを求めないため採らない。
- **スコープを絞った代償**: 当初想定した `calendar`・マスタ系はキャッシュ対象外となり、キャッシュの効果範囲はメンバー閲覧の 2 サーフェスに限定される。ただしこの 2 つが元動機（繁忙期のメンバー同時閲覧）の実体であり、`calendar`/マスタ系は主に MANAGER の編集経路（低同時数）で使われるため、性能上の主目的は損なわれない。将来、除外した read もキャッシュしたくなった場合は、下記のサーバ側不変条件を先に強制することが前提になる。
- **ADR 0004 の適用範囲を更新する**: ADR 0004 は「レート制限は認証系エンドポイントのみ・IP キー」と定めていたが、本 ADR は安全不変条件 6 のため**認証済み read にもレート制限を導入し、キーを JWT 安定ユーザー ID とする新 binding／ミドルウェアを追加**する。これは ADR 0004 の「認証済み CRUD には適用しない」という記述を部分的に置換する意図的な範囲拡張であり、**本 ADR 0013 を最新の決定として ADR 0004 をこの点で上書き（オーバーライド）する**（ADR 0004 自体は書き換えない）。既存の IP キー・認証系レート制限（login/callback/招待検証）はそのまま維持する。
- **キャッシュとは独立に存在するサーバ側不変条件のギャップ（本 ADR で新たに作る問題ではなく、除外した read を将来キャッシュするための前提として記録する。別コミット・別チケットで対応）**:
  1. `PUT /shifts/assignments` の資格要件判定は `selectInstructorIdsWithFrameCertification(db, frameId, { activeOnly: false })` を使い、**無効化済み資格も要件充足に数える**。有効資格のみで判定すべき。
  2. `POST /instructors/:id/certifications` は資格 ID の存在のみ確認し、**`is_active` を検証していない**。無効資格の割当を拒否すべき。
  3. `PUT /shifts/assignments` は**同日二重割当をサーバ側で拒否していない**（クライアント UI のみが `calendar` から警告）。サーバ側でも検証・拒否すべき。
  - これらを強制するまで、`certifications`・`calendar` 等の該当 read はキャッシュしない（安全不変条件 5）。
- **「エッジ応答の鮮度」と「画面表示の鮮度」を分けて、両方を鮮度 SLA で bound する**: エッジ応答の古さ（上限は機構的に非保証だが実務上 `waitUntil 寿命＋TTL`）と、画面表示の古さ（TanStack Query 支配）は別物である。**従来この 2 つ目は本 ADR の対象外だったが、シフト表が業務指示である以上「開いたままの画面が任意に古い」ことは許容できない**ため、上記「担保機構」を本変更のスコープに取り込み、画面鮮度も SLA 内に収める。具体的には (1) mutation 時に `agenda`/`attendance` を invalidate（クライアントに再取得を促す。ただしエッジは TTL のみ・delete しないため、これは即時反映ではなく最大エッジ TTL 遅れ）、(2) `refetchInterval≈TTL`（別クライアントの変更を定期再取得で反映）。これにより、これまで「フォーカス/再マウントまで無期限に古い」だった開きっぱなし画面が、**再取得＋エッジ TTL 律速で概ね ≤ 2 分で最新化**される。編集ループとの非干渉も保たれる: キャッシュ対象 2 サーフェスは、編集グリッドが競合判定に使う `calendar`/`assignment-editor`/`list` とは別系統であり、(1) の invalidate 追加は表示更新のみで編集の競合ロジックには影響しない。
- **実装上の要点**: `cache.put` は `executionCtx.waitUntil` でレスポンスをブロックしない。**キャッシュ制御は 2 系統に分離する（安全不変条件 2）**——エッジに `put()` する複製には TTL 用の `Cache-Control: max-age=60` を付け、クライアントへ返す MISS/HIT レスポンスは `Cache-Control: no-store, private` に置き換える。キャッシュ対象レスポンスが `Set-Cookie` を持たないこと（`agenda`/`attendance` は持たない）を前提とする。
- **必須テスト**: 実 D1 統合テスト（ADR 0007）で、①`agenda`/`attendance` の 2 回目リクエストが `X-Cache: HIT` になる ②HIT/MISS いずれのクライアント返却レスポンスも `Cache-Control: no-store` を持つ ③Cookie を外した同一 URL 要求が（キャッシュ有無に関わらず）401 になり前セッションのボディを再利用しない ④非並行の通常系で、書き込み → TTL 経過後の直接 GET が最新値を返す（happy path の失効・再 populate）。**④は並行下の厳密な鮮度上限を主張しない**——前述の通り Cache API は後着 put を防げず、遅延した古い put による上限非保証のレースは機構上の既知の制約として受容する（表示専用ゆえ許容、安全不変条件 5）。したがって本テストは「並行 put 競合が無い経路での失効動作」を確認するに留め、鮮度の厳密上限保証は受理条件に**含めない**。⑤鮮度 SLA の担保機構として、(a) 割当 mutation 後に `agenda`/`attendance` のクエリキーが invalidate されること、両クエリに `refetchInterval` が設定されていること、**および `ShiftAgendaViewer` の過去ページ（`pastPages`）も mutation 後に更新／破棄され古い業務指示を表示し続けないこと**（クライアントのユニット/コンポーネントテスト）。加えて (b) **ウォーム済みエッジエントリからの実レスポンス本文が、書き込み後 SLA 内（TTL 失効後）に更新済みへ収束すること**を実 D1 統合テストで検証する（invalidate の発火確認だけに留めず、「再取得が古い本文を再表示しない」を本文レベルで確認する。前述の通り mutation invalidate は即時反映ではなくエッジ TTL 律速のため、収束は SLA 内で判定する）。⑥キャッシュキー衛生（安全不変条件 3）: (a) 未知 query 付き要求が 400 で拒否される、(b) 意味的に等価な非正規化 query（`dates` の順序違い・重複、`limit` の等価表現）が**同一キャッシュエントリ**に解決し 2 回目が `X-Cache: HIT` になる、を検証する。⑦キャッシュ汚染・D1 増幅の bound（安全不変条件 6）: (a) canonical 形状表に従い、非 canonical な `dates` 集合（`UpcomingShifts` のユーザー可変集合を含む）・窓外の `cursor`・`limit ≠ 14` は**キャッシュをバイパス**する（`cache.put` されず、ホットエントリを追い出さない）、(b) canonical パターン（`attendance` の today/tomorrow、窓内 `agenda`）は 2 回目が `X-Cache: HIT`、(c) 認証済み read のレート制限が**ユーザー単位（JWT `user.userId` キー）**で効く——**同一 IP の別ユーザーは互いの上限に影響しない**（同一 NAT の巻き添え 429 が起きない）こと、および**同一ユーザーが同一ロケーション内で閾値を超えて連打すると 429** になること、(d) **正規利用パターン（ダッシュボード初回表示＋ agenda ページング数回＋ 60s ポーリング相当）が初期閾値（60 req/60s・burst 20）で 429 にならない**こと、を検証する。**複数 POP をまたぐ合算上限や「D1 に一切到達しない」ことは検証対象にしない**——不変条件 6 の通り、これは POP 単位・結果整合のベストエフォート防御であり厳密保証しないため（残余リスクは受容）。⑧キャッシュ障害時の fail-open（安全不変条件 7）: 例外を投げる Cache テストダブルで、(a) `cache.match` 失敗時に D1 直読みで 200 を返す（5xx にならない）、(b) `cache.put` 失敗がレスポンスに影響しない、を検証する。
- API 形状は raw JSON + Hono RPC（ADR 0005）、書き込みは Drizzle D1 batch（ADR 0006）、テストは実 D1 統合テスト（ADR 0007）を踏襲する。CONTEXT.md は変更しない（本決定はインフラであり、ドメインのユビキタス言語ではない）。
