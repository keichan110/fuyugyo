## 2. 確認の範囲と読み方

- 「アサーション」欄は、テスト本体を読んで確認した内容。名前だけを確認して本体を読んでいないものは「名前のみ」と書く。
- 「実行」欄の PR は `quality-check.yml`（`test` ジョブの Vitest + カバレッジ、`e2e` ジョブの `@smoke` のみ）、リリースは `release.yml` の全件 E2E（`pnpm run test:e2e:release`）。Vitest はリリースでは再実行されない（§4）。
- 不足の区分: **未検証**＝実装はあるがテストが確認していない／**未実装**＝仕様上あるべき制御が実装に無い、または仕様が未確定で要確認。
- 重大度は、本番データの破損・権限の越境・公開内容の誤りにつながるものを「高」、誤った状態が残るが業務上回復できるものを「中」、表示・補助的なものを「低」とした。
- 競合更新の現在のテストは、古い画面の値（`expectedRevision`／`expectedShiftId`）を**逐次に**再送して 409 になること、および `db.batch` に入れた DB ガードが失敗したとき全体がロールバックされることを確認している。複数リクエストの真の同時実行はこのベースラインでは**検証していない**（可能かどうかも未調査）。以降「並行は未検証」と書く。
- テスト本体を読んで確認した範囲は、`shift-publication.integration`・`shift-staffing-requirements.integration`・`shift-publication-migration`・`shift-view.integration`（ヘルパーと describe／it の構成、下書き・公開に関する記述の有無）・`auto-assign-context.integration`・`auto-assign-solver`・`auto-assign-regression`（不変条件の本体）。他のファイルのアサーション欄は前担当の読み取りに基づき、全件を再確認してはいない。

## 6. main との比較手順（CI を変更せずに再現する）

自動の差分コメントは作らない。比較する 2 つの SHA で**同一条件**の計測を取り、4 指標と母数を並べる。以下は `<main-wt>`（main の SHA）と `<target-wt>`（対象の SHA）の 2 つの worktree がある前提。

**実行時の注意点**

- `coverage-report.mjs` の CLI は、カレントディレクトリを基準に `vitest.config.ts` の閾値を読み、`coverage-summary.json` の絶対パスを相対化して glob と照合する。**計測した worktree をカレントディレクトリにして実行する**（別の場所で実行すると glob に一致せず、ファイル数が 0 になる）。
- CLI は率だけを表示し、**母数（覆われた数／総数）を表示しない**。母数は下記の手順 4 で JSON から集計する。
- 「未カバー分岐の上位 10 ファイル」の表は、この変更が入った `coverage-report.mjs` にしか無い。この変更の取り込み前の `main` にはスクリプトに表が無い（基点の未カバー上位表は §1 に記録済み）。取り込み後の main 同士を比べるまでは、**対象側のスクリプトのパスを指定して**両方の summary に当てる（スクリプトは Node 標準モジュールだけで動き、リポジトリ内の他ファイルに依存しない）。

**手順**

1. 比較の基準（`main` の SHA）と対象（PR の head または候補の SHA）を決め、SHA・計測日時を記録する。古い成果物は再利用しない。
2. それぞれを別のクリーンな worktree に用意する（`git worktree add <dir> <SHA>`）。依存を導入し、各 worktree で `pnpm run test:coverage` を実行する。**閾値判定が成功しても失敗しても**、`coverage/coverage-summary.json` が出ていればその値を記録する（失敗した場合はその事実も記録する）。
3. 各 worktree で、**対象 SHA の `coverage-report.mjs`** を使って表を出す（`<main-wt>` では main 側にスクリプトが無くても動く）:

   ```bash
   cd <main-wt>   # 次に <target-wt> でも同様に実行
   COVERAGE_SHA=<SHA> node <target-wt>/.github/scripts/coverage-report.mjs coverage/coverage-summary.json
   ```

   出力は、全体と閾値 glob の率、および未カバー分岐が多い上位 10 ファイル（未カバー数・総数・Branches 率）。閾値の列には**その worktree の** `vitest.config.ts` の値が使われる。

4. 母数は次のスクリプトで出す（任意の場所に保存し、各 worktree で実行する。`coverage-summary.json` の `lines`/`statements`/`functions`/`branches` の `covered`/`total` を合算する）:

   ```js
   // denominators.mjs — 各 worktree のルートで: node denominators.mjs coverage/coverage-summary.json
   import { readFileSync } from 'node:fs';
   import { matchesGlob, relative } from 'node:path';

   const summary = JSON.parse(readFileSync(process.argv[2], 'utf8'));
   const metrics = ['lines', 'statements', 'functions', 'branches'];
   const files = Object.keys(summary)
     .filter((key) => key !== 'total')
     .map((key) => [relative(process.cwd(), key), summary[key]]);
   const print = (label, list) =>
     console.log(
       label,
       `${list.length} files`,
       ...metrics.map((m) => {
         const covered = list.reduce((sum, [, c]) => sum + c[m].covered, 0);
         const total = list.reduce((sum, [, c]) => sum + c[m].total, 0);
         return `${m} ${covered}/${total}`;
       }),
     );
   print('全体', files);
   for (const glob of ['src/server/**', 'src/features/*/api.ts', 'src/features/*/schema.ts']) {
     print(
       glob,
       files.filter(([path]) => matchesGlob(path, glob)),
     );
   }
   ```

   基点（63bcaf9）の `coverage-summary.json` に対する出力は §1 の母数と一致することを確認済み（250 files、Lines 2833/5592 など）。

5. **対象範囲が異なる比較は無効**: ファイル数（250 等）や `include`／`exclude` が両者で違う場合は、差を「ファイルの増減」として説明するか、比較しない。母数（総数）が変わった理由（新規ファイル・分岐の増減）を併記する。
6. 差の読み方: 率だけでなく、覆われた数と総数の両方を見る。総数が増えて率が下がる場合は、未カバーの追加を指す。UI を足しただけで全体が下がることがあるため、業務リスクは server・api・schema の値と §3 の不足で判断する。
7. 未カバー分岐の位置が必要な場合は `pnpm exec vitest run --coverage --coverage.reporter=json --coverage.reporter=json-summary --testTimeout=20000` で `coverage/coverage-final.json` を出し、`branchMap` の位置をソースと照合する（設定は変更しない。生の成果物はコミットしない）。
