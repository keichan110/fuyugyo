# シフトの明示的な作成/削除を廃し、割り当て駆動の暗黙ライフサイクルにする

## Status

accepted

## Context

シフト確認・設定画面のフルリニューアル（#159）で、設定画面を「1部門 × シフト種別（行）× 当月の全日（列）」の月マトリクスに作り替える。週末（土日祝）主体・平日は縮小営業/部門により休校、という運用のもと、割り当て担当が大量の枠を素早く組めることが目的である。

現行の Shift API は「日付 × 部門 × シフト種別」で一意な勤務枠（Shift）に対し、明示的な作成（POST）・更新（PATCH）・削除（DELETE）を提供する。設定画面も枠を1つずつ選んで作成/保存/削除する操作前提になっており、「1枠ずつが遅い」という痛みの一因になっていた。

一方、ドメイン上は既に **休校日 = 1件も Shift が入っていない日**（マスタを持たず暗黙導出）と定義している（CONTEXT.md「稼働」）。つまり「枠が存在するか」と「その枠で開講するか」は実質同義であり、枠を人配置とは独立に明示管理する必然性が薄い。

## Decision

**Shift の明示的な作成/削除を廃止し、割り当て（ShiftAssignment）の有無で Shift のライフサイクルを暗黙的に駆動する。**

- API は `(date, departmentId, shiftTypeId)` 単位で「割り当て集合を丸ごと設定する」upsert に一本化する。
- 空の枠に最初の Instructor を割り当てた瞬間に Shift を生成する。
- 枠から全 Instructor を外し、割り当てが 0 件になった時点で Shift 自体を削除する。
- 備考（description）はこの upsert に同梱する。割り当てが 0 件かつ備考も無い枠は Shift として残さない。

これにより設定画面の思考順序は「誰を入れるか」だけになり、「作成」「削除」ボタンは UI から消える。休校/開講の状態は割り当ての有無と常に一致する。

## Considered Options

- **明示的な作成/削除を維持する**: ライフサイクルは明確だが、枠ごとに作成→保存→（不要なら）削除の操作が残り、リニューアルの主目的（週末を一気に埋める）を達成できない。却下。
- **「開講予定・人未定（募集中）」を 0 名の枠として永続化する**: 先に開講枠を決めてから人を埋める運用には向くが、休校日の暗黙導出（0件=休校）と矛盾し、モデルに「開講だが 0 名」という第3状態を持ち込む。今回の週末主体・人配置ドリブンの運用実態には不要と判断し、スコープ外とした（#159 Out of Scope）。

## Consequences

- **delete API が存在しない**のは意図的である。将来「なぜ枠を明示削除できないのか」と疑問に思う読者のために本 ADR を残す。削除は「全員外す」で表現される。
- 備考は割り当てが残る枠にのみ付随する。全員外すと枠ごと消えるため、空枠に備考だけを残すことはできない。
- 休校日/稼働日の暗黙導出（CONTEXT.md）と一貫する。「0件=休校」がライフサイクルからも保証される。
- API 形状は raw JSON + Hono RPC（ADR 0005）、書き込みは Drizzle D1 batch（ADR 0006）を踏襲する。upsert 内の生成/削除は原子的に扱う。
- テストは外部から観測できる振る舞い（最初の割り当てで枠が現れる／全員外すと枠が消える／備考の扱い）を実 D1 統合テスト（ADR 0007）で境界検証する。
