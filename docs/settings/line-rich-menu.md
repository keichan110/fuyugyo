# LINE リッチメニューの公開

GitHub Actions の手動ワークフロー `Publish LINE Rich Menu` で、デフォルト用と連携済み用のリッチメニューを公開・更新する。定義と画像は `scripts/line-rich-menu/` で版管理する。

## メニュー

| 用途       | 画像                    | 適用先                          | 操作                                                  |
| ---------- | ----------------------- | ------------------------------- | ----------------------------------------------------- |
| デフォルト | `assets/default.jpg`    | デフォルトのリッチメニュー      | 全面で LIFF URL を開く                                |
| 連携済み   | `assets/instructor.jpg` | エイリアス `fuyugyo-instructor` | 上段で LIFF URL を開く。下段の 3 操作は postback のみ |

下段の postback の `data` は左から `action=team-schedule`・`action=my-schedule`・`action=announcements`。Webhook の受信側との契約のため、変更する場合は受信側も合わせる。連携済み用をユーザーへ個別に割り当てる処理はこのワークフローに含まず、[アプリが行う](#アプリによる個別割り当て)。

タップ領域・画像・LIFF URL を変えると別の版になる。版は定義と画像のハッシュを含む管理名 `fuyugyo-richmenu:<用途>:<SHA-256>` で識別する。この形式に完全一致しないメニューは変更も削除もしない。画像は JPEG、1 MB 以下で、定義の `size` と同じ寸法にする。

## 事前準備

公開先ごとに GitHub Environment（Settings → Environments）を用意し、次を Environment に登録する。

| 名前                                  | 種類     | 値                                                                                  |
| ------------------------------------- | -------- | ----------------------------------------------------------------------------------- |
| `LINE_MESSAGING_CHANNEL_ACCESS_TOKEN` | Secret   | 対象の Messaging API チャネルのチャネルアクセストークン                             |
| `LINE_LIFF_URL`                       | Variable | その環境の LIFF URL（`https://liff.line.me/...`）                                   |
| `LINE_OFFICIAL_ACCOUNT_ID`            | Variable | 公開先の LINE 公式アカウント ID。`@` を含むベーシック ID またはプレミアム ID を書く |

`LINE_OFFICIAL_ACCOUNT_ID` がトークンのアカウントと一致しない場合は、何も変更せずに失敗する。

各 Environment では Deployment branches を `main` に限定する。`production` の Required reviewers はこのワークフローにも適用されるため、実行には承認が必要になる。

## 実行

1. Actions → `Publish LINE Rich Menu` → Run workflow を開き、`main` を選ぶ。
2. `environment` に公開先を指定する。
3. 初回は他の入力を空のまま実行する。公開済みの版がある状態で定義や画像を変える場合は、次の「アプリ側の割り当てとの協調」を済ませて `assignment_stopped` を有効にする。
4. 実行画面の Summary で、対象環境・適用した ID・削除と保持した旧版を確認する。

ワークフローはリポジトリ全体で 1 件ずつ実行する。実行中のものは取り消さないが、待機中の実行は後から起動した実行に置き換えられる。移行の途中で実行を手動キャンセルしない。

### 処理の順序

1. 公式アカウント ID を照合し、同じ管理名の重複と未完了の移行がないことを確認する。
2. 両方のメニューを再利用または作成し、画像を登録して、取得した画像がリポジトリの画像と一致することを確認する。
3. デフォルトのメニューとエイリアス `fuyugyo-instructor` を新版へ切り替える。
4. 旧版ごとに一括置換で個別の割り当てを新版へ移し、状態照会で `succeeded` を確認する。
5. デフォルトとどのエイリアスからも参照されていないことを確認して、旧版を削除する。

## アプリによる個別割り当て

アプリ（Worker）は、次の操作でユーザーの個別リッチメニューを切り替える。

| 契機                                                       | 操作                                                     |
| ---------------------------------------------------------- | -------------------------------------------------------- |
| 有効な未紐付けユーザーをインストラクターに紐付ける         | エイリアス `fuyugyo-instructor` が指すメニューを割り当て |
| 有効かつ紐付け済みのユーザーが友だち追加・ブロック解除する | 同上（Webhook の `follow` イベント）                     |
| インストラクター紐付けを解除する                           | 個別のメニューを解除し、デフォルト用へ戻す               |

紐付け先の付け替えでは LINE API を呼ばない。

### 前提

- LINE Login のチャネルと Messaging API のチャネルは、同じプロバイダーに作る。LINE ユーザー ID はプロバイダーごとに異なるため、別のプロバイダーではログインで保存した ID に割り当てられない。
- Worker の Secret `LINE_MESSAGING_CHANNEL_ACCESS_TOKEN` に、公開先と同じ Messaging API チャネルのアクセストークンを登録する。
- 友だち追加時に割り当てるには、[Webhook](line-messaging-webhook.md) の URL とシークレット（`LINE_MESSAGING_CHANNEL_SECRET`）を設定し、「Webhookの利用」を有効にする。

### 制約

- 割り当て・解除の失敗は再試行せず、紐付けの操作は成功のまま Sentry に通知する。通知には操作名と HTTP ステータスまたは失敗種別だけを含む。
- LINE は、友だち未追加やブロック中のユーザーへの割り当て・解除に 200 を返しても反映しないことがある。友だち追加前の紐付けは友だち追加時に反映する。ブロック中に紐付けを解除すると、ブロック解除後に旧メニューが残ることがある（未紐付けのユーザーの友だち追加ではメニューを操作しない）。
- 同じユーザーへの操作が同時に実行されると、LINE 側の反映順が入れ替わることがある。D1 と LINE の間の順序は保証しない。

## アプリ側の割り当てとの協調

アプリがエイリアスから旧版の ID を取得した直後に移行と削除が進むと、削除する版がユーザーに割り当てられ、そのユーザーのメニューが失われる。割り当て処理の実装と自動で協調できるまでは、旧版がある実行の前に次を行う。

1. アプリ側の個別割り当て処理を停止する。アプリに停止の切り替えはないため、管理画面でのインストラクター紐付け・解除を控え、LINE Developers コンソールの「Webhookの利用」を無効にする。無効の間に友だち追加したユーザーには割り当てられない。
2. 処理中の割り当てリクエストがすべて完了したことを確認する。
3. `assignment_stopped` を有効にして実行する。
4. 旧版の削除まで成功してから割り当て処理を再開する。失敗した場合は停止したまま復旧する。

割り当て処理を含むアプリを公開先にデプロイしていない場合は、停止するものがないためそのまま有効にしてよい。

## 失敗時の再実行

移行を始めた版は、完了するまで同じ内容で再実行する。次の版は完了後に公開する。

以前の版への切り戻しも別の版の公開にあたるため、移行の完了後に行う。移行の途中の切り戻しは LINE 側の状態だけでは中断した公開の再開と区別できず、ワークフローが停止しないことがある。受付済みの一括置換が後から完了すると、削除する版にユーザーが移るおそれがある。

- 同じ版で再実行するには、失敗した実行の「Re-run failed jobs」を使う。同じコミットと入力が使われる。Environment の `LINE_LIFF_URL` は再実行時の値になるため、完了まで変更しない。
- 入力（`batch_request_ids` など）を変える場合は新しく実行する。`main` の定義と画像が失敗した版から変わっていないことを先に確認する。
- 一括置換の再開キーとリクエスト ID の状態照会は 14 日間有効なため、期限内に完了させる。

| 失敗した箇所                       | 状態                                 | 対応                                                                                        |
| ---------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------- |
| アカウント ID の照合               | 変更なし                             | トークンと `LINE_OFFICIAL_ACCOUNT_ID` を確認する                                            |
| メニュー作成（成否を確認できない） | 切り替え前                           | 時間をおいて再実行する。作成済みなら再利用される                                            |
| 画像の登録・照合                   | 切り替え前                           | 再実行すると同じメニューに登録する。不一致が続く場合は下の「手動対応」へ                    |
| デフォルト・エイリアスの切り替え   | 一方だけ新版の場合がある。旧版は残る | 同じ版で再実行する                                                                          |
| 一括置換（失敗・応答なし）         | 新版へ切り替え済み。旧版は残る       | 同じ版で再実行する。同じ再開キーで再送される                                                |
| 一括置換（状態確認が時間切れ）     | 同上                                 | ログの `旧ID:新ID:リクエストID` を `batch_request_ids` に指定すると、再送せず状態を照会する |
| レート制限（429）                  | 到達した段階まで反映。旧版は残る     | 1 時間以上おいて同じ版で再実行する。一括置換は 1 時間に 3 回まで                            |
| 旧版が参照されていて削除しない     | 移行済み。旧版は残る                 | 旧版を指すエイリアスを確認して外し、再実行する                                              |
| 削除                               | 移行済み。旧版は残る                 | 同じ版で再実行する                                                                          |

`batch_request_ids` の指定は、旧 ID と新 ID の組が一致する置換にだけ使う。

## 手動対応

次の場合、ワークフローは安全のため停止するか旧版を残す。対象を確認してから Messaging API で整理する。

- **同じ管理名のメニューが複数ある**: どれもデフォルト・エイリアス・ユーザーに使われていないことを確認し、1 件を残して削除する。
- **登録済みの画像が一致しない**: そのメニューが未使用なら削除して再実行する。作り直しても一致しない場合は、LINE が取得時に画像を変換している可能性があるため、実行を中止して照合方法を見直す。
- **画像が未登録の旧版を保持した**: 公開は成功している。画像のないメニューはユーザーに割り当てられないため、不要なら削除する。
- **前回の移行が完了していない**: エラーに表示された版のコミットで定義と画像を `main` に戻し、完了させてから次の版を公開する。

```bash
# トークンは履歴に残らないよう、プロンプトから読み込む
read -rs LINE_TOKEN

# 一覧
curl -H "Authorization: Bearer $LINE_TOKEN" https://api.line.me/v2/bot/richmenu/list
# 現在のデフォルトとエイリアス
curl -H "Authorization: Bearer $LINE_TOKEN" https://api.line.me/v2/bot/user/all/richmenu
curl -H "Authorization: Bearer $LINE_TOKEN" https://api.line.me/v2/bot/richmenu/alias/list
# 削除（取り消せないため ID を確認してから実行する）
curl -X DELETE -H "Authorization: Bearer $LINE_TOKEN" https://api.line.me/v2/bot/richmenu/<richMenuId>
```

## 実機確認

まず検証用の公式アカウントの Environment で公開し、確認してから本番に実行する。初回は特に、画像の照合を含めてワークフローが成功することを確認する。

1. 個別のメニューが割り当てられていないアカウントで公式アカウントのトークを開く。反映されない場合はトーク画面を開き直す。
2. デフォルト用の画像が表示され、画像の四隅と中央のどこをタップしても LIFF が開くことを確認する。
3. アプリを使わずに連携済み用を確認する場合は、確認用の自分のアカウントに一時的に割り当てる。ユーザー ID は LINE Developers コンソールの「あなたのユーザー ID」で確認する。

   ```bash
   curl -H "Authorization: Bearer $LINE_TOKEN" https://api.line.me/v2/bot/richmenu/alias/fuyugyo-instructor
   curl -X POST -H "Authorization: Bearer $LINE_TOKEN" https://api.line.me/v2/bot/user/<userId>/richmenu/<richMenuId>
   ```

4. 上段のタップで LIFF が開くことを確認する。
5. 下段の左・中央・右をタップし、トークに発言が表示されないことを確認する。Webhook の受信ログを確認できる場合は、`postback.data` が左から `action=team-schedule`・`action=my-schedule`・`action=announcements` であることを確認する。
6. 各領域の境界付近をタップし、意図した操作になることを確認する。
7. 割り当てを解除し、デフォルト用に戻ることを確認する。

   ```bash
   curl -X DELETE -H "Authorization: Bearer $LINE_TOKEN" https://api.line.me/v2/bot/user/<userId>/richmenu
   ```

アプリからの割り当ては、検証用の公式アカウントを友だちに追加したアカウントで、インストラクターの紐付け・解除と、紐付け済みのままのブロック解除により切り替わることを確認する。

LINE Official Account Manager で作成したメニューは管理対象外。Messaging API で設定したデフォルトは、管理画面のデフォルトより優先して表示される。

参考: [Messaging API リファレンス（リッチメニュー）](https://developers.line.biz/ja/reference/messaging-api/#rich-menu)
